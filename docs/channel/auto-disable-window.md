# 渠道自动禁用窗口策略说明

本文档说明渠道自动禁用相关设置的当前语义，适用于管理后台中的失败重试与自动禁用配置。

## 行为概述

当前版本的自动禁用策略已经从“连续失败/连续超时”调整为“时间窗口内累计次数”：

- `窗口内失败禁用阈值`
- `窗口内超时禁用阈值`
- `失败/超时统计窗口（秒）`

命中阈值后，渠道会按现有机制进入自动禁用状态。

## 与旧行为的差异

旧行为强调“连续”：

- 同一渠道连续失败达到阈值才触发自动禁用
- 同一渠道连续超时达到阈值才触发自动禁用
- 中间一旦成功，计数容易被清零

新行为强调“窗口内累计”：

- 只要同一渠道在统计窗口内累计达到阈值，就会触发自动禁用
- 成功请求不会立即把窗口内历史失败全部清空
- 非超时错误也不会把超时窗口的历史记录直接清空
- 超过统计窗口的旧记录会自动过期

这更适合多渠道重试场景，因为同一渠道在实际流量中往往很难满足严格的“连续失败”条件。

## 建议配置

可先使用以下保守配置作为起点：

- `窗口内失败禁用阈值 = 3`
- `窗口内超时禁用阈值 = 2`
- `失败/超时统计窗口（秒） = 300`

适用场景：

- 上游偶发 `503`、`TLS`、`temporarily unavailable` 时，希望坏渠道能较快被摘除
- 超时链路希望更快止损

如果上游本身波动较大，可以适当放宽为：

- `窗口内失败禁用阈值 = 5`
- `窗口内超时禁用阈值 = 3`
- `失败/超时统计窗口（秒） = 600`

## 立即禁用规则

以下规则仍然保留原有逻辑，不依赖窗口累计：

- `401`
- 明确的 `invalid_api_key`
- `account_deactivated`
- `billing_not_active`
- `insufficient_quota`
- `permission_error`
- 后台配置的自动禁用状态码与关键字

这些错误通常表示渠道本身已失效或当前 key 不可恢复，命中后会直接进入自动禁用流程。

## 兼容性说明

为避免数据库配置迁移，本次仅调整了语义，没有更改原有配置键名：

- `AutomaticDisableConsecutiveFailureCount`
- `AutomaticDisableConsecutiveTimeoutCount`

虽然键名中仍保留 `Consecutive`，但运行时语义已经变为“窗口内累计次数”。

后台页面会显示新的中文文案：

- `窗口内失败禁用阈值`
- `窗口内超时禁用阈值`
- `失败/超时统计窗口（秒）`

## 当前限制

当前仍然是“达到阈值后自动禁用”，不是“短暂熔断后自动恢复”。

也就是说：

- 适合快速摘除明显异常渠道
- 但不等同于完整的熔断器模型
- 如果需要“自动冷却 5 分钟后恢复探测”，需要后续再扩展 cooldown / half-open 机制
